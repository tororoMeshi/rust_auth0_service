# 認証基盤の設計仕様（基盤方針）

## 1. 文書の目的

### 中心原則

認証の責務と、サービスの責務を分離する。

### この認証基盤への具体化

複数のWebサービスが共通認証基盤を利用する構成を、設計上の前提として固定する。本書では、目的、対象範囲、システム境界、論理的責務、不変条件を定義する。

本書は基盤方針を定める。状態遷移、公開契約の詳細、保存形式、トークン方式、実装タスクは定めない。

## 2. 認証基盤の目的

認証基盤の目的は、複数のWebサービスを、一つの共通認証基盤によって利用可能にすることである。

ユーザーは、認証基盤で一度本人確認を行う。その後、認証基盤を利用する複数のWebサービスへログインできる。

各Webサービスは、Googleなどの外部認証を個別に実装しない。外部認証との接続、本人確認、共通認証状態の管理は、共通認証基盤の責務とする。

認証基盤は、本人確認と共通認証状態を扱う。各Webサービス固有の業務権限、業務データ、画面、業務処理まで一元管理するとは定めない。

## 3. 対象範囲

### 今回固定する範囲

対象範囲は、次の論理的な機能である。

- 外部認証プロバイダーとの本人確認
- 外部の本人情報と内部ユーザーの対応付け
- 共通認証状態の管理
- 認証結果をWebサービスへ安全に引き渡すこと
- 認証の開始、完了、失敗、期限切れ、ログアウトの管理
- 認証に必要な秘密情報の管理
- 認証結果が対象Webサービス向けであることを識別できること
- 複数のWebサービスが利用できる公開認証インターフェースの提供

現在実装する外部認証プロバイダーはGoogleである。これは現在の実装範囲であり、認証基盤の恒久的な仕様をGoogle専用にすることを意味しない。

### 対象範囲外または後続判断

次の事項は、今回の基盤方針では固定しない。

- 各Webサービス固有の業務権限、ロール設計、業務データ
- ポータルの画面設計やチャットなど個別サービスの機能
- GitHub認証、Microsoft認証、Apple認証の実装
- 任意のOIDCプロバイダーを動的登録する機能
- アカウント統合UI、管理画面、組織・テナント管理、課金
- 詳細な監査ログ
- 状態遷移の詳細
- APIエンドポイントの詳細
- DBスキーマの詳細
- JWTまたはセッション方式の最終決定
- Kubernetes上の最終的なPod分割

対象範囲外とは、永久に実装しないという意味ではない。必要性と設計を後続工程で判断する事項である。

## 4. システム境界

設計上の必須境界は、次の二層である。

```text
共通認証基盤
────────────
各Webサービス
```

共通認証基盤と各Webサービスは、論理的に別のシステムである。各Webサービスのバックエンドは、認証基盤の内部実装から完全に分離する。

各Webサービスは、公開された認証契約だけを知る。認証基盤の内部サービス構成、内部セッション形式、内部ユーザーテーブル構造を前提にしてはならない。

各Webサービスは、次を行わない。

- Google OAuthを直接処理する
- 将来追加される外部認証プロバイダーを直接処理する
- 認証基盤のPostgreSQLを直接参照する
- 認証基盤のRedisを直接参照する
- 認証基盤の内部セッション形式へ依存する
- 認証基盤の内部ユーザーテーブル構造へ依存する
- 認証基盤の秘密署名鍵を保持する
- 認証基盤内部のサービス構成を知ることを前提にする

この境界は、同じリポジトリに配置されているか、同じKubernetesクラスタに配置されているかによって変わらない。

論理的な責務の境界と、Kubernetes上のDeploymentまたはServiceの境界は別である。外部プロバイダー接続と内部認証コアを別Podにすることは、今回の必須条件ではない。現在の `rust-auth0-service` と `uniauth` が別Serviceであることは、現在の実装上の事実として扱う。

## 5. コンポーネントの論理的責務

### 外部プロバイダー接続

外部プロバイダー接続は、次を担当する。

- 外部認証の開始
- 外部プロバイダーからのcallback処理
- 外部プロバイダー固有の検証
- 外部ユーザー情報の取得
- 外部情報を共通外部ID形式へ変換すること

この責務は、Google固有の外部仕様や識別子を内部認証コアへ持ち込まない。外部プロバイダーから得た本人情報は、共通形式へ変換してから内部認証コアへ渡す。

### 内部認証コア

内部認証コアは、次を担当する。

- 内部ユーザーの識別
- 外部IDとの対応付け
- 共通認証状態の管理
- Webサービスへ渡す認証結果の生成
- ログアウトまたは失効に必要な状態管理

内部認証コアは、特定プロバイダーの外部仕様を知らない。`google_id` のような特定プロバイダー専用概念を中心にしない。

### Webサービス

Webサービスは、次を担当する。

- 認証基盤へログインを要求すること
- 認証基盤から公開契約に従って認証結果を受け取ること
- 受け取った結果を検証すること
- 各Webサービス固有の処理を行うこと
- 各Webサービス固有の認可判断を行うこと

Webサービスは、共通認証の結果を利用して自サービスの処理を保護する。ただし、認証基盤の内部状態を直接操作しない。

## 6. Webサービスとの契約上の境界

認証基盤とWebサービスの接続点は、公開された認証契約である。Webサービスが利用できるのは、この契約で明示された情報と振る舞いだけである。

認証結果は、どのWebサービス向けであるかを識別できなければならない。Webサービスは、受け取った認証結果を自ら検証し、検証に成功した場合だけ自サービスの処理へ進める。

認証基盤の内部DB、Redis、内部セッション形式、内部サービス間通信は、Webサービスとの契約に含めない。認証基盤の内部実装が変わっても、公開契約が変わらない限り、各Webサービスは変更を要求されない。

認証と認可は分離する。認証基盤は本人確認と共通認証を提供する。各Webサービスは、自サービス固有の業務権限と業務上の認可判断を担当する。

公開契約の具体的な形式は、今回決めない。

## 7. 外部認証プロバイダーとの境界

外部認証プロバイダー固有処理と、内部認証コアは論理的に分離する。

外部プロバイダー接続側は、プロバイダー固有の認可、callback、検証、本人情報取得を担当する。内部認証コアへは、共通形式に変換した本人情報だけを渡す。

認証コアはGoogle固有の外部仕様を知らない。内部ユーザーの識別子は、外部プロバイダーのユーザーIDと別に持つ。プロバイダーが追加されても、各Webサービスの実装を変更しない。プロバイダーが追加されても、認証コア全体を作り直さない。

現時点ではGoogle以外を実装しない。GitHub、Microsoft、Apple、汎用OIDCの具体的な実装設計は、今回作成しない。空実装、プレースホルダー、汎用プラグイン機構も作成しない。

## 8. 不変条件

### 境界

- 認証基盤と各Webサービスは独立してデプロイ可能である。
- 各Webサービスは、認証基盤の内部DBとRedisを直接参照しない。
- 各Webサービスは、外部認証プロバイダーと直接通信しない。
- 認証基盤の内部実装変更によって、公開契約が変わらない限り各Webサービスを変更しない。
- 外部認証プロバイダーの追加によって、各Webサービスを変更しない。

### 本人識別

- 外部プロバイダーのユーザーIDと、認証基盤内部のユーザーIDを区別する。
- 内部ユーザーの識別子を、特定プロバイダーのIDと同一視しない。
- メールアドレスだけを無条件に同一人物判定の主キーにしない。
- プロバイダー固有情報は、境界で共通形式へ変換する。

### 秘密情報

- 外部プロバイダーのclient secretを各Webサービスへ渡さない。
- 認証結果の発行に使用する秘密鍵を各Webサービスへ渡さない。
- 各Webサービスが認証結果を偽造できる共有方式を前提にしない。
- 共有秘密鍵を各Webサービスへ配布する方式を、認証契約の前提にしない。
- Secretの具体的な管理方式は、後続工程で決める。

### 状態

- 認証処理中の一時状態と、認証完了後の状態を区別する。
- 認証基盤の共通認証状態と、各Webサービス固有の状態を区別する。
- 取得できなかった認証情報を正常値として扱わない。
- 認証失敗を認証成功として扱わない。
- 有効期限切れや失効済みの状態を有効として扱わない。

### 実装範囲

- 現時点で実装する外部プロバイダーはGoogleのみである。
- 将来利用するかもしれないプロバイダーの空実装を追加しない。
- 必要になる前に汎用プラグイン機構を追加しない。
- 現在必要な公開契約を超える汎用化を行わない。

## 9. 現時点で固定しない事項

次の事項は、今回の設計方針では決めない。

- 状態遷移の詳細
- APIエンドポイント、リクエスト、レスポンスなどの詳細
- DBスキーマ、マイグレーション、保存項目などの詳細
- JWTまたはセッション方式、そのClaimや検証方式
- 認証結果の具体的な公開形式
- 認証基盤内部のサービス分割とKubernetes上のPod配置
- Secretの具体的な保管、配布、ローテーション方式
- 各Webサービス固有の認可、ロール、業務セッションの設計

これらを未決定のままにすることは、境界と責務を未定義にすることではない。今回固定した不変条件と責務を満たす具体化を、後続工程で行う。

## 10. 現在の実装との対応関係

以下は `docs/auth-current-state.md` で確認できる現在の実装を、今回定義した論理的責務へ対応付けたものである。現在の実装の事実と、設計上の位置付けは別の列に記載する。

| 現在のコンポーネント | 現在確認できる責務 | 設計上の論理的位置付け | 今回確定しないこと |
| ---------- | --------- | ----------- | --------- |
| `rust-auth0-service` | Google認証の開始とcallback、外部ユーザー情報の取得、`uniauth` 呼び出し、認証Cookieの発行・削除 | 外部プロバイダー接続を担う現在の実装コンポーネント。内部認証コアとの境界に接続する位置 | 外部プロバイダー接続と内部認証コアの最終的なプロセス、Deployment、Pod分割 |
| `uniauth` | ユーザーのupsert、認証結果の発行、Redis上のログインセッション作成・削除・検証 | 内部認証コアを担う現在の実装コンポーネント | 内部ユーザー識別、外部ID対応付け、認証結果、失効状態の最終形式 |
| `portal_backend` | 認証Cookieを検証し、ログインユーザー情報を返す | 共通認証基盤を利用するWebサービスのバックエンド | Webサービスとの公開契約、自サービス固有の認可、業務セッションの最終設計 |
| `portal` | ログイン後の画面を提供し、認証サービスのURLを利用して認証を開始する | 共通認証基盤を利用するWebサービスのフロントエンド。認証基盤そのものではない | ポータル固有の画面、業務処理、最終的な配備構成 |
| PostgreSQL | `uniauth` がユーザー情報を保存・更新する永続ストア | 内部認証コアが利用する内部データストア。Webサービスからは境界の内側 | 保存構造、移行方式、保持項目、アクセス方式 |
| Redis | OAuth中のWebセッションと、`uniauth` のログインセッションを保持・検証するストア | 認証基盤が利用する内部状態ストア。Webサービスからは境界の内側 | 状態の分類、TTL、キー形式、失効方式、Redisの配置 |

`portal` と `portal_backend` は、同じリポジトリに配置されている。しかし、設計上は共通認証基盤を利用するデモWebサービスであり、認証基盤そのものではない。ポータル固有の画面、業務処理は、認証基盤の責務に含めない。

現在の実装に `google_id` や共有Cookieが存在することは、現在の実装上の事実である。それらの存在によって、今回定義した内部ユーザー識別やWebサービスとの境界を変更しない。現在の実装との差分の修正案や移行方法は、本書では扱わない。

## 11. 状態遷移設計の目的

状態遷移設計は、認証処理と認証状態の成立条件を定義する。画面遷移を定義するものではない。

状態遷移設計の目的は次のとおりである。

- 認証処理の現在地を明確にする。
- 成功、失敗、期限切れ、失効を混同しない。
- 取得できなかった値を正常値として扱わない。
- 不正な順序で処理を進めない。
- 再送、二重callback、二重交換、二重ログアウトの扱いを明確にする。
- 認証基盤の状態とWebサービスの状態を分離する。

## 12. 状態機械の分離

認証に関する状態は、認証基盤全体で一つにまとめない。次の四つの状態機械を独立して扱う。

```text
外部認証トランザクション
        │ 本人確認成功
        ▼
共通認証セッション
        │ 特定サービスへのログイン要求
        ▼
Webサービス向け認証引き渡し
        │ 引き渡し成功
        ▼
Webサービス側の認証状態
```

これは一つの状態機械ではない。それぞれで、状態の所有者、有効期限、終了条件、再実行条件が異なる。

## 13. 外部認証トランザクション

外部認証トランザクションは、外部認証プロバイダーとの本人確認処理を表す。Googleは現在の実装例であるが、状態名と遷移は特定プロバイダーに依存しない。

```text
未開始
  ↓ 認証開始
外部認証待機中
  ↓ callback検証と本人情報取得の成功
外部ID確認済み
  ↓ 内部ユーザーの解決成功
完了
```

次の入力は、終了理由を伴う `終了` へ遷移させる。

```text
外部認証待機中
  ├─ 検証失敗
  ├─ プロバイダー拒否
  ├─ 必須情報不足
  ├─ 期限切れ
  └─ 内部処理失敗
        ↓
終了
```

`終了` は一つの終了状態である。Google拒否、state不一致、通信失敗、期限切れなどを恒久的な独立状態にはしない。`終了` には終了理由を保持する設計概念を置く。

| 状態 | 状態の意味 | 許可される入力 | 次状態 | 状態所有者 | 状態終了時に不要となる情報 | 再実行方法 |
| --- | --- | --- | --- | --- | --- | --- |
| 未開始 | 外部認証トランザクションがまだ存在しない | 認証開始 | 外部認証待機中 | 認証基盤 | なし | 新しいトランザクションを開始する |
| 外部認証待機中 | 外部プロバイダーの本人確認とcallbackを待っている | 対応するcallback、期限切れ、拒否、検証失敗 | 外部ID確認済みまたは終了 | 認証基盤 | callback検証用の一時情報 | 失敗または期限切れなら新しいトランザクションを開始する |
| 外部ID確認済み | 外部情報の検証と共通外部IDへの変換が完了した | 内部ユーザーの解決 | 完了または終了 | 認証基盤 | 外部認証中だけ必要な一時情報 | 解決失敗なら新しいトランザクションを開始する |
| 完了 | 本人確認と内部ユーザーの解決が成立した | 後続処理からの参照 | 状態機械上は遷移しない | 認証基盤 | 外部認証中の一時情報 | 巻き戻さず、新しい認証が必要なら新しいトランザクションを開始する |
| 終了 | 成功せず閉じた。終了理由を持つ | 参照または結果通知 | 状態機械上は遷移しない | 認証基盤 | 処理継続に不要な一時情報 | 新しいトランザクションを開始する |

次を不変条件とする。

- 認証開始前にcallbackを受理しない。
- 対応する一時状態がないcallbackを成功扱いしない。
- stateなどの検証に失敗したcallbackを本人確認成功として扱わない。
- 必須の本人情報を取得できなかった場合は完了へ進めない。
- 完了または終了したトランザクションを巻き戻さない。
- 再試行時は、新しいトランザクションを開始する。
- 外部プロバイダー固有の処理結果は、共通外部ID形式へ変換してから次へ進める。

## 14. 共通認証セッション

共通認証セッションは、認証基盤内で成立する共通認証状態を表す。保存先、Cookie形式、JWT形式、Redis使用の有無は本章で決めない。

```text
不在
  ↓ 外部認証トランザクション完了
有効
  ├─ 有効期限切れ
  ├─ 共通ログアウト
  ├─ 管理上の失効
  └─ 状態不整合
        ↓
終了
```

`終了` は一つの状態である。終了理由として、少なくとも `expired`、`logged_out`、`revoked`、`invalidated` を区別できるようにする。

| 状態 | 成立条件 | 有効と判断する条件 | 許可される処理 | 終了条件 | 状態所有者 |
| --- | --- | --- | --- | --- | --- |
| 不在 | 有効な共通認証セッションがない | 有効とは判断しない | 完了した外部認証からの開始 | 外部認証トランザクション完了による開始 | 認証基盤 |
| 有効 | 外部認証トランザクションが完了し、必須情報がそろっている | 期限内で、失効や不整合がなく、必要情報を検証できる | 特定Webサービスへの引き渡し要求、ログアウト、失効 | 期限切れ、共通ログアウト、管理上の失効、状態不整合 | 認証基盤 |
| 終了 | 有効状態を継続できない | 有効とは判断しない | 終了理由の参照、必要な結果通知 | 状態機械上は遷移しない | 認証基盤 |

次を不変条件とする。

- 外部認証トランザクションが完了していなければ有効にしない。
- 有効期限切れを有効として扱わない。
- 失効済みを有効として扱わない。
- 認証に必要な必須情報が欠けている状態を有効として扱わない。
- 共通認証セッションの有効性と、個別Webサービスのログイン状態を同一視しない。
- 共通認証セッション終了後の各Webサービスへの影響は、後続工程で契約として決める。

## 15. Webサービス向け認証引き渡し

Webサービス向け認証引き渡しは、有効な共通認証セッションを利用して、特定のWebサービスへ認証結果を渡す処理を表す。ここで渡すものは、方式を特定しない「認証引き渡し情報」と表現する。

```text
未開始
  ↓ Webサービスから認証要求
引き渡し準備中
  ↓ 対象サービスと戻り先の検証成功
引き渡し可能
  ↓ 正常な受領
使用済み
```

次の入力は `終了` へ遷移させる。

```text
引き渡し準備中 または 引き渡し可能
  ├─ 対象サービス不一致
  ├─ 戻り先不一致
  ├─ 共通認証セッション無効
  ├─ 期限切れ
  ├─ 重複使用
  └─ 検証失敗
        ↓
終了
```

| 現在状態 | 入力またはイベント | 成立条件 | 次状態 | 副作用 | 拒否時の扱い |
| --- | --- | --- | --- | --- | --- |
| 未開始 | Webサービスから認証要求 | 要求元を認識できる | 引き渡し準備中 | 一時的な引き渡し処理を開始する | 成立条件を満たさなければ終了する |
| 引き渡し準備中 | 対象サービスと戻り先の検証 | 許可された対象と戻り先であり、共通認証セッションが有効 | 引き渡し可能 | 認証引き渡し情報を準備する | 終了し、認証成功を通知しない |
| 引き渡し可能 | Webサービスによる受領 | 対象、戻り先、期限、未使用性を検証できる | 使用済み | Webサービスが認証結果を受領する | 終了し、Webサービス側の成功にしない |
| 使用済み | 再受領または再送 | 成立しない | 使用済み | 追加の成功副作用を発生させない | 拒否する |
| 終了 | 再送または遅延入力 | 成立しない | 終了 | 不要な一時情報を破棄する | 拒否する。再要求は新しい引き渡しとする |

次を不変条件とする。

- 認証結果がどのWebサービス向けかを識別できる。
- 他のWebサービス向けの認証結果を受理させない。
- 登録または許可されていない戻り先へ認証結果を渡さない。
- 一回限りの情報として設計される場合、使用済みを再使用させない。
- 期限切れを受理させない。
- 共通認証セッションが無効なら新しい引き渡しを成立させない。
- 引き渡し失敗をWebサービス側のログイン成功として扱わない。

認可コード、JWT、Cookieなどの具体方式は、この工程では確定しない。

## 16. Webサービス側の認証状態

Webサービス側の認証状態は、各Webサービスが所有する状態である。認証基盤の内部状態ではない。

```text
未認証
  ↓ 認証引き渡しの検証成功
認証済み
  ├─ ローカルログアウト
  ├─ ローカル有効期限切れ
  ├─ 認証結果の検証失敗
  └─ 共通認証側の失効を反映
        ↓
未認証
```

| 現在状態 | 入力またはイベント | 成立条件 | 次状態 | 副作用 | 拒否時の扱い |
| --- | --- | --- | --- | --- | --- |
| 未認証 | 認証引き渡しの受領 | 公開契約に従って検証に成功する | 認証済み | Webサービス側の認証状態を開始する | 未認証のままにする |
| 認証済み | 利用要求 | Webサービス側で有効と判断できる | 認証済み | 業務処理を認証済みとして扱う | 業務処理を進めない |
| 認証済み | ローカルログアウト、期限切れ、検証失敗、共通側の失効反映 | 終了条件が成立する | 未認証 | Webサービス側の認証状態を終了する | 成功扱いにしない |
| 未認証 | 再送または不正な受領 | 成立しない | 未認証 | なし | 拒否する |

各Webサービスが保持する具体的な状態形式は、各サービスの設計事項である。Webサービスは認証基盤のDBやRedisを直接参照して状態判定してはならない。認証基盤との公開契約を通じて必要な情報を受け取る。

Webサービス固有のロールや業務権限は、この状態とは別に判断する。`portal` はこの状態機械を実装するデモWebサービスである。

共通認証側の失効を即時反映するか、有効期限で反映するか、照会で反映するかは今回決めない。

## 17. ログアウトと失効の関係

### ローカルログアウト

特定Webサービス内の認証状態だけを終了する。ローカルログアウトと共通ログアウトは同じ処理ではない。

### 共通ログアウト

認証基盤の共通認証セッションを終了する。一つのWebサービスからログアウトしただけで、必ず全サービスをログアウトさせるとは今回決めない。

### 失効

セキュリティ、管理操作、状態不整合などにより、認証基盤が共通認証状態を無効にする。共通ログアウト後に各Webサービスへどのように反映するかは、公開契約の後続設計で決める。

ブラウザ上の情報を削除しただけで、サーバー側の有効状態が必ず失効したとはみなさない。サーバー側の状態を削除しただけで、配布済みの認証結果が必ず無効になるともみなさない。何を正本とするかは後続工程で決める。

## 18. 不正遷移と再実行

次を四つの状態機械に共通する規則とする。

- 現在状態から許可されていない入力は拒否する。
- 拒否した入力によって状態を進めない。
- 同一callbackの重複処理を複数の認証成功にしない。
- 同一引き渡し情報の重複使用を複数のログイン成功にしない。
- 完了済みまたは終了済みの処理を巻き戻さない。
- 再試行は新しい処理単位を作成する。
- タイムアウト後の遅延応答を成功扱いしない。
- 一部の副作用だけが成功した場合を、全体成功として扱わない。
- 状態更新と重要な副作用の整合性を後続実装で保証する。
- 状態が不明な場合は成功側へ倒さない。

冪等性の具体的なキーやトランザクション方式は、まだ決めない。

## 19. 状態遷移の共通不変条件

### 正確性

- 成功条件がすべて成立した場合だけ成功状態へ進む。
- 取得失敗、保存失敗、検証失敗を成功として扱わない。
- 状態不明を有効状態として扱わない。

### 分離

- 外部認証状態、共通認証状態、引き渡し状態、Webサービス状態を混同しない。
- 一つの状態機械の終了が、別の状態機械の終了を自動的に意味するとは限らない。
- 状態間の連動は公開契約として明示する。

### 有効期限

- 期限切れ後に新しい成功遷移を認めない。
- 有効期限の確認に失敗した場合は有効とみなさない。
- 時刻取得失敗や時刻不整合を正常として扱わない。

### 所有権

- 各状態には一つの明確な所有者を定める。
- Webサービスは認証基盤所有の状態を直接変更しない。
- 認証基盤はWebサービス固有の業務状態を直接変更しない。

## 20. 後続工程で決める事項

次の事項は、状態機械の分離と不変条件を満たす具体化として、後続工程で決める。

- 各状態の保存先
- 状態識別子の形式
- 有効期限の具体値
- Cookieの具体構成
- JWTまたはサーバーセッションの選択
- 認証引き渡しの具体方式
- 認可コードを使用するか
- PKCEを使用するか
- トークンClaims
- 失効の伝達方法
- ローカルログアウトと共通ログアウトのAPI
- 冪等性キー
- DBトランザクション
- Redisの使用範囲
- 状態イベントの監査方法
- Kubernetes上の配置
- 実装タスク

## 21. データ設計の目的

データ設計は、外部プロバイダー上の本人、認証基盤内部のユーザー、認証処理中の情報を混同しないために行う。

次を目的として固定する。

- 外部プロバイダーの識別子と内部ユーザーを混同しない。
- 外部プロバイダーを追加しても内部ユーザーの意味を変更しない。
- 各Webサービスを認証基盤の保存構造から分離する。
- 取得できなかった情報と、取得した結果がfalseまたは空であった情報を区別する。
- 一時データと永続的な本人対応付けを区別する。
- 状態機械の所有者とデータの所有者を一致させる。
- 現在必要な最小限の概念だけを定義する。

## 22. 識別子の分類

外部プロバイダー、内部ユーザー、Webサービス、処理単位の識別子は、それぞれ別の目的で使用する。識別子同士を兼用しないことを基本とする。

| 識別子 | 発行または決定する主体 | 識別対象 | 安定性 | 他の識別子との兼用 |
| --- | ----------- | ---- | --- | --- |
| 内部ユーザーID | 認証基盤 | 認証基盤内部のユーザー | 外部プロバイダーやWebサービスに依存せず安定 | 外部subject、メールアドレス、Webサービス識別子とは兼用しない |
| プロバイダー識別子 | 外部プロバイダー接続と認証基盤の契約 | 外部認証プロバイダーの種類 | 対応するプロバイダーを示す間は安定 | subject単独や内部ユーザーIDとは兼用しない |
| 外部subject | 外部プロバイダー | そのプロバイダー内の本人 | 同一プロバイダー内での識別に使用 | 内部ユーザーIDやメールアドレスとは兼用しない |
| Webサービス識別子 | 認証基盤とWebサービスの契約 | 認証要求または認証結果の対象Webサービス | 対象サービスを識別する間は安定 | ユーザー識別子や処理識別子とは兼用しない |
| 認証処理識別子 | 認証基盤 | 外部認証トランザクションや認証引き渡しなどの一時処理単位 | 処理の有効期間に限って使用 | 恒久的なユーザー識別子とは兼用しない |

プロバイダー識別子の現在実装上の例は `google` である。具体的な列挙型や登録方式は決めない。外部subjectは、外部プロバイダーが発行した識別子を意味解釈せず文字列として扱う。数値のように見える場合も、内部で数値演算や大小比較を行う前提にしない。

## 23. 内部ユーザー

認証基盤内部のユーザーを、概念上の `InternalUser` として定義する。

```text
InternalUser
- internal_user_id
- lifecycle_status
- created_at
```

これは概念モデルである。SQLのカラム名や型として確定しない。

`internal_user_id` は認証基盤が発行する、内部ユーザーの安定した識別子である。特定の外部プロバイダー、メールアドレス、Webサービスに依存しない。`lifecycle_status` は、ユーザーが認証基盤上で利用可能かを表す概念である。具体的な状態一覧は今回確定しない。

内部ユーザーについて次を固定する。

- 外部プロバイダーのユーザーIDとは別である。
- メールアドレスを内部ユーザーIDとして使用しない。
- 表示名や画像URLを本人識別の主キーにしない。
- Webサービスごとのユーザー情報をすべて保持する場所ではない。
- 各Webサービス固有のプロフィールや設定は各Webサービスが所有する。
- 外部プロバイダーが一時的に利用できなくても、内部ユーザーの識別子自体は変わらない。

名前、メール、画像などを `InternalUser` 本体へ複製保存するかは、まだ最終決定しない。

## 24. 外部ID

外部プロバイダー上の本人との対応を、概念上の `ExternalIdentity` として定義する。

```text
ExternalIdentity
- provider
- subject
- internal_user_id
- observed_attributes
- linked_at
```

`provider` と `subject` の組 `(provider, subject)` が、外部の本人を識別する。`subject` 単独では一意とみなさない。`observed_attributes` は、外部プロバイダーから取得し、共通形式へ変換した属性の概念である。具体的な保存形式は決めない。

外部IDについて次を固定する。

- 同じ `(provider, subject)` を複数の内部ユーザーへ関連付けない。
- メールアドレスだけで既存の内部ユーザーへ自動的に関連付けない。
- プロバイダーからsubjectを取得できない場合は、外部ID確認成功としない。
- 外部IDは認証基盤が所有し、各Webサービスは直接変更しない。
- プロバイダー固有のアクセストークンやリフレッシュトークンを `ExternalIdentity` の必須要素にしない。

現在必要な本人確認だけで利用するため、外部プロバイダーのアクセストークンやリフレッシュトークンは、標準では永続保存しない。将来、外部APIを継続利用する別機能が必要になった場合は、認証とは別の目的と契約で判断する。

## 25. 内部ユーザーと外部IDの対応関係

概念上の対応関係は次のとおりである。

```text
InternalUser 1
  └─ ExternalIdentity 1..n
```

一つの内部ユーザーが、複数の外部IDを持ち得る。一方、現在の最小実装では、一つのGoogle外部IDから一つの内部ユーザーを解決する構成から開始してよい。

### 設計上許容する関係

一つの内部ユーザーが、複数の外部IDを持ち得る。

### 現在実装する範囲

Googleの一つの外部IDから、一つの内部ユーザーを解決する。

### 現在実装しないもの

- 複数プロバイダーのアカウント連携
- 同一プロバイダー内の複数アカウント連携
- メールアドレスによる自動統合
- ユーザー向けの連携解除画面
- 管理者によるアカウント統合
- 重複ユーザーの自動マージ

将来許容する関係を理由に、現在これらの機能を実装しない。

## 26. 外部プロバイダー情報の共通形式

外部プロバイダー接続から内部認証コアへ渡す概念上の共通形式を、`NormalizedExternalIdentity` とする。

```text
NormalizedExternalIdentity
- provider
- subject
- email
- email_verification
- display_name
- picture_url
```

必須項目は `provider` と `subject` である。`email`、`email_verification`、`display_name`、`picture_url` は任意項目である。各項目の具体的な保存形式は決めない。

`email_verification` は、少なくとも次の概念を区別する。

- `verified`
- `unverified`
- `unknown`

取得できなかったことを `unverified` と同一視しない。

次を不変条件とする。

- `provider` または `subject` がなければ外部ID確認成功としない。
- `email` がなければ架空のメールアドレスを生成しない。
- `display_name` がなければ外部subjectから表示名を自動生成しない。
- `picture_url` がなければ存在しないURLを作らない。
- 取得できなかった値を空文字で正常値として補完しない。
- 任意属性の欠落によって、既存の有効な属性を無条件に消去しない。
- 外部プロバイダー固有のレスポンス全体を、そのまま内部認証コアの契約にしない。

現在のGoogleレスポンスからの対応は次のとおりである。これはGoogle以外のマッピングを定義するものではない。

| Googleレスポンス | 共通形式 | 扱い |
| --- | --- | --- |
| `id` | `subject` | 必須。意味解釈せず外部subjectとして扱う |
| Googleという接続元 | `provider` | 必須。現在実装上の値の例は `google` |
| `email` | `email` | 任意。取得できない場合は欠損のまま扱う |
| `verified_email` | `email_verification` | 任意。取得値に応じて `verified` または `unverified` とする。取得できない場合は `unknown` |
| `picture` | `picture_url` | 任意。取得できない場合は欠損のまま扱う |
| 表示に利用する外部属性 | `display_name` | 任意。現在のGoogleレスポンスで対応する値がなければ設定しない |

## 27. データの所有権

| データ概念 | 所有者 | 作成主体 | 読み取り可能な境界 | 直接変更可能な主体 |
| ----- | --- | ---- | --------- | --------- |
| `InternalUser` | 認証基盤 | 内部認証コア | 認証基盤内部と公開契約で許可された情報の利用者 | 認証基盤 |
| `ExternalIdentity` | 認証基盤 | 内部認証コア | 認証基盤内部 | 認証基盤 |
| `NormalizedExternalIdentity` | 外部プロバイダー接続が生成し、内部認証コアへ渡す | 外部プロバイダー接続 | 外部プロバイダー接続と内部認証コアの境界 | 生成元と受領側の責務範囲のみ |
| 外部認証トランザクションの一時情報 | 認証基盤 | 外部プロバイダー接続 | 認証基盤内部 | 認証基盤 |
| 共通認証セッション | 認証基盤 | 内部認証コア | 認証基盤と公開契約で許可された利用者 | 認証基盤 |
| 認証引き渡し情報 | 認証基盤 | 認証基盤 | 対象Webサービスとの公開契約の範囲 | 認証基盤 |
| Webサービス側の認証状態 | 各Webサービス | 各Webサービス | 当該Webサービス | 当該Webサービス |
| Webサービス固有プロフィール | 各Webサービス | 各Webサービス | 当該Webサービス | 当該Webサービス |
| Webサービス固有ロール・権限 | 各Webサービス | 各Webサービス | 当該Webサービス | 当該Webサービス |

`InternalUser` と `ExternalIdentity` は認証基盤が所有する。`NormalizedExternalIdentity` は外部プロバイダー接続が生成し、内部認証コアへ渡す。各Webサービスは認証基盤の内部レコードを直接変更しない。各Webサービスは自サービス固有のプロフィール、ロール、権限を所有する。認証基盤は各Webサービスの業務データを直接変更しない。

同じKubernetesクラスタや同じリポジトリに存在しても、所有権は変わらない。

## 28. 状態機械とデータの関係

第13章から第16章の四つの状態機械が扱うデータ概念を次に整理する。

| 状態機械 | 主なデータ | 一時または永続 | 所有者 | 終了時の扱い |
| ---- | ----- | ------- | --- | --- |
| 外部認証トランザクション | 一時的な認証処理識別子、検証用情報、戻り先情報、`NormalizedExternalIdentity` | 認証処理識別子と検証用情報は一時。共通形式は後続の対応付けに渡す | 認証基盤 | 不要な一時情報を破棄し、完了または終了を巻き戻さない |
| 共通認証セッション | 内部ユーザーID、成立時刻、有効性、期限または終了理由に相当する概念 | 共通認証状態として管理。具体的な保存期間は未定 | 認証基盤 | 有効状態を終了し、終了理由を区別できるようにする |
| 認証引き渡し | 対象Webサービス、認証対象の内部ユーザー、期限、使用状況に相当する概念 | 特定サービスへの一時情報 | 認証基盤 | 使用済みまたは終了として扱い、再利用させない |
| Webサービス側認証状態 | 公開契約から得た内部ユーザー識別情報と、自サービス内の状態 | 各Webサービスが管理する状態 | 各Webサービス | 自サービス側の状態を終了し、業務データの扱いは自サービスで判断する |

`未開始`、`不在`、`未認証`などは、必ずしも保存レコードを意味しない。状態図に存在することだけを理由に、空のレコードや状態行を作成する設計にはしない。

## 29. データに関する不変条件

### 識別

- 内部ユーザーIDと外部subjectを兼用しない。
- providerなしでsubjectを解釈しない。
- メールアドレスだけで同一人物と断定しない。
- Webサービス識別子とユーザー識別子を兼用しない。
- 一時的な処理識別子を恒久的なユーザー識別子として使用しない。

### 欠損

- 未取得と空文字を同一視しない。
- `unknown` と `false` を同一視しない。
- 必須値の欠損を仮の値で補完して成功扱いしない。
- 一時的な取得失敗によって、既存の有効な永続値を無条件に削除しない。

### 所有権

- Webサービスから認証基盤内部データを直接更新させない。
- 認証基盤からWebサービス固有データを直接更新しない。
- 外部プロバイダーのレスポンスを未検証のまま永続的な本人情報としない。

### 最小性

- 現在使用しない外部プロバイダー用データを作成しない。
- 汎用属性保存機構を先回りして作成しない。
- 外部レスポンス全体を保存することを標準にしない。
- 将来のアカウント統合機能のための状態や履歴を先回りして追加しない。

## 32. 公開契約設計の目的

公開契約は、複数のWebサービスが同じ認証基盤を利用するための境界を定義する。

次を目的として固定する。

- 複数のWebサービスが同じ認証基盤を利用できる。
- Webサービスごとに認証要求と認証結果を区別する。
- 他サービス向けの認証結果を利用させない。
- 認証基盤の内部構造をWebサービスへ公開しない。
- 外部プロバイダーの変更をWebサービスへ波及させない。
- 戻り先の差し替えを防ぐ。
- 認証途中の情報と認証完了結果を区別する。
- ブラウザから渡された未検証情報を本人情報として信用しない。
- 新しいWebサービス追加時に必要な契約を明確にする。
- 現在必要な最小限の契約だけを定義する。

Webサービスは、認証基盤の内部実装ではなく、公開された認証契約だけを利用する。

## 33. Webサービスの登録

認証基盤を利用するWebサービスを、概念上の `RegisteredWebService` として定義する。

```text
RegisteredWebService
- service_id
- lifecycle_status
- allowed_return_targets
```

これは概念モデルであり、SQLテーブルや設定ファイルの形式として確定しない。

`service_id` は、認証基盤内でWebサービスを識別する安定した識別子である。表示名、URL、Kubernetes Service名、ドメイン名を、そのまま必須の識別子として兼用するとは決めない。

`lifecycle_status` は、Webサービスが認証基盤を利用可能かを表す概念である。具体的な状態一覧は今回決めない。利用停止されたWebサービスへ新しい認証結果を発行しないことを不変条件とする。

`allowed_return_targets` は、認証処理完了後に戻ることを許可された場所の集合である。具体的な保存形式は決めない。ワイルドカードによって任意のサブドメインや任意のパスを広く許可することを標準方針にしない。

## 34. Webサービス識別子

第22章で定義したWebサービス識別子は、公開契約の対象を特定するために使用する。

- 認証要求には対象Webサービスの識別が必要である。
- 認証引き渡し情報にも対象Webサービスの識別が必要である。
- 認証要求時と受領時で同じ対象Webサービスであることを確認する。
- Webサービス識別子を内部ユーザーIDと兼用しない。
- Webサービス識別子を認証処理識別子と兼用しない。
- Webサービス識別子を表示名や戻り先URLから毎回推測しない。
- Webサービスのドメイン変更によって内部ユーザーIDが変化しない。
- 外部認証プロバイダーはWebサービス識別子を知る必要がない。

具体的な文字形式、長さ、生成方式は後続工程へ残す。

## 35. 認証要求

Webサービスから認証基盤へ渡す概念上の認証要求を、`AuthenticationRequest` として定義する。

```text
AuthenticationRequest
- service_id
- return_target
- request_correlation
```

これは概念モデルであり、具体的な通信形式やAPIとして確定しない。

`service_id` は認証を要求するWebサービスを識別する。`return_target` は認証処理後に戻る候補であり、登録済みの許可対象と一致する場合だけ使用する。`request_correlation` は認証要求と応答を対応付ける一時的な情報である。具体的な生成、保存、暗号化、名称は決めない。

認証要求について次を固定する。

- 未登録の `service_id` を受理しない。
- 利用停止中のWebサービスからの要求を受理しない。
- `return_target` は登録済みの許可対象と照合する。
- ブラウザから渡された `service_id` だけを無条件に信用しない。
- ブラウザから渡された `return_target` へ無条件にリダイレクトしない。
- 認証要求に内部ユーザーIDを指定させない。
- 認証要求に外部subjectを指定させない。
- Webサービスから外部プロバイダー固有のユーザー情報を渡させない。

外部プロバイダーをWebサービス側から選択可能にするかは、今回決めない。

## 36. 認証引き渡し情報

第15章の「認証引き渡し情報」を、概念上の `AuthenticationHandoff` として定義する。

```text
AuthenticationHandoff
- handoff_id
- service_id
- internal_user_id
- issued_at
- expires_at
- usage_status
```

これは概念モデルである。ブラウザにこの構造全体を直接渡すとは決めない。各項目の具体的な形式も決めない。

`handoff_id` は一つの認証引き渡し処理を識別する一時的な識別子であり、内部ユーザーIDやWebサービス識別子と兼用しない。`service_id` は対象Webサービスを表す。`internal_user_id` は認証基盤内で確認された内部ユーザーを表し、外部subjectをそのまま使用しない。

`issued_at` と `expires_at` は発行時刻と有効期限の概念である。具体的な時刻形式と有効期間は後続工程で決める。`usage_status` は、一回限りの引き渡しとして実装する場合に、未使用、使用済み、終了などを区別する概念である。具体的な状態一覧は、状態遷移と整合する範囲で後続工程へ残す。

認証引き渡しについて次を固定する。

- 対象 `service_id` を持つ。
- 有効期限を確認できる。
- 対応する内部ユーザーを識別できる。
- 他サービス向けとして受領できない。
- 期限切れを受領できない。
- 終了済みまたは使用済みを新しい成功として扱わない。
- 外部プロバイダーのアクセストークンをWebサービスへ渡さない。
- 外部プロバイダーのsubjectを、Webサービスが必要とする標準識別子にしない。
- 外部プロバイダーのレスポンス全体を渡さない。
- 認証基盤の内部セッションIDを、そのまま公開契約にするとは決めない。

## 37. Webサービスによる受領と検証

Webサービスのバックエンドが、公開契約に従って認証結果を受領し、検証する責務を持つ。

- 認証結果の検証はWebサービスのバックエンドが行う。
- フロントエンドだけの判定で認証済みにしない。
- 対象 `service_id` が自サービスと一致することを確認する。
- 有効期限を確認する。
- 終了済み、使用済み、失効済みではないことを確認する。
- 認証基盤が発行した結果であることを確認する。
- 検証できない結果を認証成功として扱わない。
- 検証途中の情報をWebサービス側の認証状態として保存しない。
- 検証成功後にだけ、Webサービス側の認証状態へ遷移する。
- Webサービスは認証基盤のPostgreSQLやRedisを直接参照して検証しない。

認証基盤が発行したことを確認する具体方式は、後続工程で決める。署名検証、バックチャネル照会、交換処理などの方式は、今回採用しない。

## 38. 戻り先の検証

`return_target` は対象Webサービスの登録情報と照合する。自由入力のURLとして扱わない。

- 未登録の戻り先へ遷移しない。
- 別Webサービスの戻り先を使用しない。
- ホスト名の部分一致だけで許可しない。
- 文字列の前方一致だけで許可しない。
- URL内のユーザー情報部分を利用した偽装を許可しない。
- スキーム、ホスト、ポート、パスなど必要な要素を正規化後に比較する。
- 検証失敗時は安全な固定先へ戻すか、認証基盤上でエラー終了する。
- 検証失敗した `return_target` を応答へそのまま反映しない。

URL正規化ライブラリ、比較アルゴリズム、保存形式は今回決めない。現在の実装に許可origin判定が存在することは現状として記録するが、完成形の契約ではWebサービス単位の登録済み `return_target` との照合を基準とする。

## 39. 契約上のエラー

公開契約上の失敗を、技術スタック固有の例外ではなく、概念的なエラー分類として扱う。

- `unknown_service`
- `service_inactive`
- `return_target_not_allowed`
- `authentication_not_completed`
- `authentication_expired`
- `handoff_invalid`
- `handoff_expired`
- `handoff_already_used`
- `handoff_service_mismatch`
- `authentication_result_unverifiable`

これらは状態名として増やさない。状態遷移の終了理由または公開契約上の拒否理由として扱う。

- 外部プロバイダー固有のエラーを、そのままWebサービスとの恒久的な契約にしない。
- 内部DBやRedisのエラー詳細をWebサービスへ公開しない。
- Secret、トークン、内部識別子をエラー本文へ含めない。
- Webサービスが再認証すべきか、要求を修正すべきかを区別できる。
- HTTPステータスやJSON形式は後続工程で決める。

## 40. ログアウトに関する契約境界

### Webサービスのローカルログアウト

対象Webサービスが、自サービス内の認証状態だけを終了する。認証基盤の内部状態を直接削除しない。

### 共通ログアウト要求

Webサービスまたはユーザーが、認証基盤へ共通認証セッションの終了を要求する。要求方法と本人確認方法は後続工程で決める。

### 認証基盤による失効

認証基盤が、共通認証状態を無効にする。

次を固定する。

- ローカルログアウトAPIと共通ログアウトAPIを同一の意味にしない。
- Webサービスが認証基盤のRedisキーを指定して削除させる契約にしない。
- Webサービスが認証基盤の内部セッションID形式へ依存しない。
- 共通ログアウト後の既発行認証結果への反映方法は後続工程で決める。
- ログアウト後の戻り先も登録済みの許可対象から選ぶ。
- 任意のURLをログアウト後の戻り先として受理しない。

具体的なエンドポイントは決めない。

## 41. 公開情報と非公開情報

| 情報 | Webサービスへ公開可能か | 公開理由または非公開理由 |
| -- | ------------- | ------------ |
| `service_id` | 条件付きで可能 | 自サービス向け結果の対象確認に必要。ただし登録情報の全体は公開しない |
| `internal_user_id` | 公開可能 | Webサービスがユーザーを安定して識別するため。ただし内部保存構造は公開しない |
| 認証結果の発行時刻 | 条件付きで可能 | 有効性確認に必要な範囲で判断する。具体形式は未定 |
| 認証結果の有効期限 | 条件付きで可能 | 期限確認に必要な範囲で判断する。具体形式は未定 |
| 外部provider | 標準契約では原則非公開 | 外部プロバイダー固有情報であり、必要な場合は別の明示的契約で判断する |
| 外部subject | 標準契約では原則非公開 | 内部ユーザー識別のためにWebサービスへ渡さない |
| 外部アクセストークン | 非公開 | 外部プロバイダーの秘密情報である |
| 外部リフレッシュトークン | 非公開 | 外部プロバイダーの秘密情報である |
| Google client secret | 非公開 | 外部プロバイダー接続の秘密情報である |
| 認証基盤の秘密署名鍵 | 非公開 | 認証基盤の秘密情報である |
| 認証基盤の内部Redisキー | 非公開 | 内部保存形式であり、契約上不要である |
| 認証基盤の内部DB主キー構造 | 非公開 | 内部保存構造であり、契約上不要である |
| 共通認証セッションの内部表現 | 非公開 | 内部状態であり、公開契約と分離する |
| 認証引き渡し処理の状態 | 必要最小限のみ | 受領可否に必要な結果だけを契約で定義する |
| Webサービス固有ロール | 非公開 | 各Webサービスが所有し、認証基盤は決定しない |
| Webサービス固有プロフィール | 非公開 | 各Webサービスが所有し、認証基盤は直接管理しない |

Webサービスが外部providerを業務上必要とする場合は、標準契約ではなく別の明示的な契約として判断する。Webサービス固有情報は認証基盤が所有しない。

## 42. 公開契約の不変条件

### 対象

- すべての認証要求に対象Webサービスがある。
- すべての認証引き渡しに対象Webサービスがある。
- 対象が不明な認証結果を発行しない。
- 他Webサービス向けの結果を受理させない。

### 検証

- 戻り先を登録情報と照合する。
- 検証できない認証結果を成功扱いしない。
- 有効期限を確認できない場合は有効扱いしない。
- ブラウザから渡された本人情報を無条件に信用しない。

### 分離

- Webサービスは認証基盤の内部DBとRedisを直接参照しない。
- Webサービスは外部プロバイダーのアクセストークンを受け取らない。
- 認証基盤はWebサービス固有権限を決定しない。
- 公開契約を変更しない内部実装変更をWebサービスへ波及させない。

### 最小性

- 動的クライアント登録を先回りして作らない。

## 46. 認証方式選定の目的

本章群は、認証基盤の共通認証状態、Webサービスへの認証引き渡し、Webサービス側の認証状態を、一つの具体的な方式として固定する。

優先するのは、Webサービスを認証基盤の内部状態から分離し、他サービス向けの認証結果を利用させず、認証結果の発行権限をWebサービスへ渡さないことである。

## 47. 比較対象

比較対象は次の四つとする。

- 候補A：親ドメイン共有Cookie
- 候補B：サービス向けJWTをブラウザへ直接発行
- 候補C：一回限りの認証コードとバックチャネル交換
- 候補D：認証基盤への都度照会

候補Dは、主方式としての採用可否と、必要時の補助手段としての利用可能性を分けて評価する。

## 48. 候補方式の比較

| 評価項目 | 候補A | 候補B | 候補C | 候補D |
|---|---|---|---|---|
| 認証基盤とWebサービスの分離 | 低い。Cookie形式と親ドメイン共有に依存する | 中程度。検証契約に依存する | 高い。内部状態を交換結果として直接公開しない | 中程度。内部状態は隠せるが実行時に強く依存する |
| ブラウザに露出する情報 | 長期の共通認証情報が露出する | サービス向けJWTが露出する | 短時間・不透明・一回限りの情報だけを露出する | 認証情報または照会材料を継続的に扱う |
| 他サービス向け認証結果の誤用防止 | 低い。共有Cookieの対象を分けにくい | service_id設計に依存する | 高い。コードと交換先Webサービスを結び付ける | 照会要求の対象識別に依存する |
| Webサービス追加時の変更量 | Cookie共有条件の調整が必要 | 検証鍵または検証契約の配布が必要 | 登録情報とバックチャネル契約の追加で足りる | 登録情報と実行時照会の追加が必要 |
| Webサービス側の秘密情報 | 共有Cookieの保護に依存する | HS256なら共有秘密、非対称署名なら公開鍵だけでよい | 認証結果を発行する秘密情報は不要 | 照会のためのWebサービス識別手段が必要 |
| 認証基盤の秘密鍵の保護 | Cookie方式自体では解決しない | HS256では損なう。非対称署名なら保護できる | 認証引き渡しの主方式では秘密署名鍵を配布しない | 主方式では秘密署名鍵を配布しない |
| Webサービスが認証結果を偽造できる可能性 | 共有Cookieの価値を持つ主体が広がる | HS256共有秘密なら高い | 低い。認証基盤だけが交換結果を成立させる | 照会結果自体は偽造しにくいが照会契約に依存する |
| 失効の反映 | 共有Cookieだけでは不十分 | JWT単独では期限まで遅延しやすい | 新規引き渡しは即時停止できる。既存ローカル状態は方針が必要 | 照会時に即時反映できる |
| 共通ログアウト | 共有Cookie削除とサーバー側状態の分離が難しい | 既発行JWTの扱いが難しい | 共通認証セッションを終了できる | 照会時に反映できる |
| ローカルログアウト | 共通Cookieへ影響しやすい | Webサービス側の保持方法に依存する | 自サービスのローカル状態だけを終了できる | 自サービスの状態だけを終了できる |
| 障害時の影響範囲 | Cookieが残るため挙動が不明確になりやすい | 発行済みJWTは検証できる場合がある | 新規ログインと交換だけが影響を受ける | 各利用要求または頻繁な確認が影響を受ける |
| 認証基盤への実行時依存 | 低い | 低い | ログイン時・交換時だけ必要 | 高い |
| 実装の複雑さ | 低いが境界を損なう | 中程度。鍵、Claims、誤用防止が必要 | 中程度。短命状態と一回限り交換が必要 | 低い開始点でも可用性・負荷設計が必要 |
| 状態数 | 少ないが状態の責務が混ざる | 中程度 | 明確に分離できる | 照会結果とローカル状態の関係が増える |
| ネットワーク通信量 | 低い | 低い | ログインごとに一回のバックチャネル交換 | 利用ごと、または頻繁に発生する |
| 現在の実装からの移行難易度 | 低いが完成形として維持できない | 中程度 | 中程度 | 中程度 |
| 複数Webサービスへの適合性 | 低い。親ドメインとCookie共有に縛られる | 中程度。厳密な対象検証が必要 | 高い。Webサービスごとに交換先を分離できる | 中程度。実行時依存が増える |
| 不変条件との整合性 | 低い | 中程度 | 高い | 中程度 |
| 外部プロバイダー追加への影響 | Webサービス側へ共有情報の影響が残る | 発行Claimsの契約へ影響しやすい | 認証基盤内部の外部ID解決に閉じる | 認証基盤内部に閉じる |
| 最小構成としての妥当性 | 現在は近いが完成形として不適切 | 発行・検証の契約が先行する | 高い。必要な状態だけで成立する | 主方式としては低い。補助手段としては可能 |

候補Aの決定的な利点は実装が単純なことである。しかし、共有Cookieを標準契約にすると、Webサービスの境界、対象サービスの識別、Cookieの影響範囲を分離できない。

候補Bの決定的な利点は、認証基盤への都度接続なしにWebサービスが検証できることである。しかし、ブラウザへ認証結果を直接露出し、対象サービス制約、失効、鍵配布を同時に設計する必要がある。

候補Cの決定的な利点は、ブラウザへ長期認証結果や認証基盤内部状態を渡さず、対象Webサービスだけが認証結果を受領できることである。短時間・一回限りの状態とバックチャネル交換が必要になる。

候補Dの決定的な利点は失効を即時に確認できることである。しかし、主方式にすると全Webサービスの利用時可用性と通信量が認証基盤へ依存する。

## 49. 採用方式

認証基盤ドメイン限定の共通認証セッションと、一回限りの認証引き渡し情報のバックチャネル交換を使用し、各Webサービスは交換成功後に自サービス固有のローカルセッションを開始する。

これは候補Cを主方式として採用する決定である。候補Dの都度照会は主方式にしない。必要時の失効確認などの補助手段として後続工程で判断できる。

## 50. 共通認証セッション

共通認証セッションは認証基盤が所有する。正本は認証基盤側に置く。

ブラウザは、認証基盤ドメインで共通認証セッションへ到達するための限定的な情報を保持する。この情報はWebサービスへ直接共有しない。Webサービスは認証基盤の共通認証セッション、PostgreSQL、Redis、内部セッション形式を直接参照できない。

外部認証トランザクションが完了し、InternalUserが解決された場合だけ共通認証セッションを有効にする。期限切れ、共通ログアウト、失効、状態不整合により終了する。終了後は、新しいAuthenticationHandoffを成立させない。

共通認証セッションの保存先、状態識別子、期限の具体値は後続工程で決める。

## 51. 認証引き渡し

AuthenticationHandoffは、認証基盤が作成する短時間・一回限りの不透明な認証引き渡し情報とする。ブラウザはこの情報を対象Webサービスへ運ぶが、認証結果そのもの、共通認証セッションの値、外部provider、外部subject、外部プロバイダーのトークンは運ばない。

AuthenticationHandoffは、少なくとも対象 `service_id`、対応する `internal_user_id`、発行時刻、有効期限、使用状況に結び付く。`return_target` は対象 `RegisteredWebService` の許可済み候補と照合済みでなければならない。

対象Webサービスのバックエンドは、ブラウザから受け取った認証引き渡し情報を認証基盤へ提示し、バックチャネルで交換する。認証基盤は、対象Webサービス、期限、共通認証セッションの有効性、使用状況を確認してから交換結果を返す。

交換に成功した時点でAuthenticationHandoffは使用済みとする。使用済み、終了済み、期限切れ、対象サービス不一致、検証不能な情報の再利用は拒否する。再試行が必要な場合は、新しい認証要求と新しいAuthenticationHandoffを開始する。

## 52. Webサービス側の認証状態

Webサービス側の認証状態は各Webサービスが所有する。認証基盤の共通Cookieや内部セッションを直接利用しない。

Webサービスは、バックチャネル交換が成功した後にだけ、自サービス固有のローカル認証状態を開始する。ローカル認証状態の具体形式は、Webサービス固有CookieまたはWebサービス固有サーバーセッションのいずれかとし、認証基盤と共有しない。

ローカルログアウトは、そのWebサービスのローカル認証状態だけを終了する。共通認証セッションを終了するとは限らない。Webサービス固有のロール、業務権限、プロフィール、業務データは引き続き各Webサービスが所有する。

## 53. JWTと署名の方針

今回採用する主方式では、ブラウザへのAuthenticationHandoffにJWTを使用しない。ブラウザへ長時間有効なサービスJWTを直接渡さない。

Webサービス側のローカルセッションにJWTを使用する必要はない。各Webサービスは、自サービスの要件に応じて後続工程でローカル状態の具体形式を決める。

認証基盤とWebサービス間のAuthenticationHandoff交換結果にも、初期の主方式としてJWTを必須にしない。認証基盤がバックチャネル交換を成立させ、その結果をWebサービスが自サービスのローカル認証状態を開始するために利用する。

HS256の共有秘密鍵方式を完成形として維持しない。Webサービスへ、認証基盤が発行する認証結果を偽造可能な共有秘密を配布しない。

後続工程で交換結果に署名付き情報が必要になった場合は、認証基盤だけが秘密署名鍵を保持し、Webサービスは検証専用の公開情報だけを持つ構成を検討する。具体的なアルゴリズムは今回決めない。

## 54. Cookieの所有権とスコープ

認証基盤のCookieは認証基盤ドメインに限定する。親ドメインCookieを認証基盤とWebサービス間の標準契約にしない。

各Webサービスは、自サービスのローカル認証状態のために自サービスのCookieを持てる。このCookieの正本は、各Webサービスが所有するローカル認証状態である。

認証基盤Cookieの正本は、認証基盤側の共通認証セッションである。WebサービスCookieの正本は、各Webサービス側のローカル認証状態である。

Cookie削除だけをサーバー側失効とみなさない。サーバー側状態を削除しただけで、既にブラウザへ配布された情報が必ず無効になるともみなさない。

## 55. ログアウトと失効

ローカルログアウトは、対象Webサービスのローカル認証状態を終了する。共通認証セッションは終了しない。

共通ログアウトは、認証基盤の共通認証セッションを終了する。以後、新しいAuthenticationHandoffの発行と交換を成立させない。

認証基盤による失効は、セキュリティ、管理操作、状態不整合などにより共通認証セッションを終了する。共通ログアウトと同様に、新しい引き渡しを停止する。

共通認証セッションの終了後、既存のWebサービス側ローカルセッションを即時に全て終了させることは、最小構成では必須にしない。既存のローカルセッションは、そのWebサービスの有効期限または必要時の補助照会によって遅延反映され得る。この制約を許容する。

認証基盤への全リクエスト都度照会は導入しない。即時失効が必要な場面だけ、後続工程で失効照会を補助手段として定義できる。

## 56. 採用しない方式と理由

親ドメイン共有JWT Cookieは、認証基盤のSSO状態を複数Webサービスへ直接共有し、対象サービスの分離と失効管理を損なうため、今回の主方式として採用しない。将来も永久に禁止するとは決めないが、標準契約にはしない。

親ドメイン共有 `session_id` Cookieは、認証基盤内部セッション形式をWebサービスへ露出し、内部状態への依存を作るため、今回の主方式として採用しない。標準契約にはしない。

WebサービスへHS256共有秘密鍵を配布する方式は、Webサービスが認証結果を偽造できるため採用しない。認証基盤の発行権限を共有する方式としては採用しない。

ブラウザへ長時間有効なサービスJWTを直接渡す方式は、ブラウザ露出、誤用防止、失効反映の負担が増えるため採用しない。短命情報を含む別用途の検討を永久に禁止するものではない。

認証基盤への全リクエスト都度照会は、認証基盤への実行時依存と障害範囲を広げるため主方式として採用しない。必要時の補助照会は後続工程で判断する。

外部プロバイダーのアクセストークンまたはリフレッシュトークンをWebサービスへ渡す方式は、認証の目的を超えて外部プロバイダーの権限を配布するため採用しない。別の外部API利用目的が必要になった場合だけ、認証とは別の契約として判断する。

| `.tororomeshi.net`の共有Cookie | 親ドメイン共有を標準契約にしない | 認証基盤Cookieを認証基盤ドメインへ限定する方向 |

| HS256 | 認証基盤の発行権限を共有する方式を採用しない | 共有秘密方式を完成形にしない方向 |
| portal_backendによるJWT直接検証 | バックエンド検証責務は維持するが、検証対象がJWTではない | 認証引き渡しのバックチャネル交換へ移す方向 |

| Redis `session_id` | 内部セッション形式がブラウザへ露出している | 共通認証セッションの正本を認証基盤内に閉じる方向 |
| `/upsert_and_token` | 認証結果とセッション情報を同時に返す | InternalUser解決と共通認証セッション開始へ責務を分離する方向 |
| `/sessions/verify` | Webサービス側のJWTと内部セッションを照合する | Webサービス向けの一回限り交換へ置き換える方向 |

| `redirect` | service_idと登録済み戻り先の対応がない | `RegisteredWebService` の `return_target` 照合へ移す方向 |
| `ALLOWED_REDIRECT_ORIGINS` | origin単位の許可設定である | Webサービス単位の許可済み戻り先へ移す方向 |

## 58. 今回固定する不変条件

- 認証基盤のSSO状態をWebサービスへ直接共有しない。
- 親ドメインCookieを認証基盤とWebサービス間の標準契約にしない。
- Webサービスへ認証結果を発行可能な秘密情報を配布しない。
- AuthenticationHandoffは対象 `service_id` と結び付く。
- 他サービス向けのAuthenticationHandoffを交換できない。
- 期限切れのAuthenticationHandoffを交換できない。
- 使用済みのAuthenticationHandoffを再交換できない。
- 交換失敗をWebサービス側の認証成功にしない。
- Webサービスは交換成功後にだけローカル認証状態を開始する。
- Webサービスのローカルセッションは各Webサービスが所有する。
- 認証基盤の共通ログアウトとWebサービスのローカルログアウトを混同しない。
- Cookie削除だけをサーバー側失効とみなさない。
- サーバー側状態削除だけで配布済み情報が必ず無効になるとはみなさない。
- 不明な状態を成功側へ倒さない。

## 60. API・セッション契約の目的

公開契約は、認証基盤のSSO状態をWebサービスへ共有せず、短時間・一回限りの引き渡しとバックチャネル交換だけでWebサービスのローカル認証状態を開始するための境界である。

## 61. 認証フローの全体像

```text
Webサービスバックエンド
  | stateを生成して一時保存
  v
ブラウザ
  | GET /auth/login
  v
認証基盤
  | 共通認証セッション有効: Google認証を省略
  | 共通認証セッション不在: Google認証を実行
  v
AuthenticationHandoff発行
  | codeとstateを付けて検証済みreturn_targetへ戻す
  v
Webサービスバックエンド
  | stateを検証
  | POST /auth/handoffs/exchange
  v
認証基盤
  | service認証、期限、未使用性、対象を検証
  | codeを使用済みにする
  v
Webサービスバックエンド
  | internal_user_idを受領
  | ローカルセッションを開始
  v
ブラウザ
  | Webサービス固有Cookieを保持
```

## 62. 公開操作の一覧

| 操作 | 主体 | 対象 | 安定した公開契約か |
|---|---|---|---|
| `GET /auth/login` | ブラウザ | 認証基盤 | はい |
| Google callback | 外部プロバイダー | 認証基盤 | いいえ。外部プロバイダー接続の内部契約 |
| Webサービスcallback | ブラウザ | Webサービスの検証済み`return_target` | はい。各RegisteredWebServiceの戻り先であり、認証基盤の固定APIパスではない |
| `POST /auth/handoffs/exchange` | Webサービスバックエンド | 認証基盤 | はい |
| Webサービスの`POST /logout` | ブラウザ | Webサービスバックエンド | 認証基盤の公開契約ではない。Webサービス固有契約 |
| `GET /auth/logout` | ブラウザ | 認証基盤 | はい |
| `POST /auth/logout` | 認証基盤ドメイン上のブラウザ | 認証基盤 | はい |

## 63. ログイン開始契約

Webサービスバックエンドはログイン開始時に推測困難な`state`を生成し、自サービスの一時ログイン状態へ保存してからブラウザを`GET /auth/login`へ遷移させる。`state`は`request_correlation`の具体名であり、ユーザーID、セッションID、認証結果として使用しない。

`GET /auth/login`はクエリで`service_id`、`return_target`、`state`を受け取る。認証基盤は、登録済みサービス、利用可能状態、対象サービスに登録された完全一致のURI、`state`の存在・形式・長さの順に検証する。URIはスキーム、ホスト、ポート、パスを含む完全なURIとし、ワイルドカード、部分一致、前方一致、URLフラグメントを許可しない。初期実装ではクエリなしのcallback URIだけを許可する。

未検証の`return_target`へは成功時も失敗時も遷移しない。

## 64. 共通認証セッションによるSSO

有効な共通認証セッションがある場合、認証基盤はGoogle認証を再実行せず、新しいAuthenticationHandoffだけを発行する。SSOは外部認証を省略することであり、過去のAuthenticationHandoffを再利用することではない。共通認証セッションそのものはWebサービスへ渡さない。

## 65. 外部認証トランザクション

有効な共通認証セッションがない場合、認証基盤は外部認証トランザクションを開始する。この一時状態は`service_id`、検証済み`return_target`、`state`、有効期限、外部プロバイダーcallback検証に必要な情報と結び付く。現在の外部プロバイダーはGoogleだけである。Google callbackは認証基盤内部の外部接続契約であり、Webサービスとの安定した公開契約には含めない。

## 66. 認証引き渡しの発行

認証基盤は、内部ユーザー確認後に短時間・一回限り・不透明な`handoff_code`を生成する。コードは`service_id`、`internal_user_id`、検証済み`return_target`、発行時刻、有効期限、使用状態、元の共通認証セッション、必要なら認証成立時刻に結び付く。

ブラウザは検証済み`return_target`へ、`code`と`state`だけを付けて遷移する。`code`は`handoff_code`である。`internal_user_id`、外部provider、外部subject、メール、表示名、外部トークン、共通認証セッションID、JWT、Webサービス認証用Secretは渡さない。

## 67. Webサービス側のstate検証

Webサービスバックエンドは、callback受領後かつ交換前に`state`を検証する。`state`がない、対応するローカル開始状態がない、不一致、期限切れ、使用済みの場合は交換しない。検証成功後、ローカル開始状態を再利用不能にする。`state`検証失敗を認証基盤側の認証成功で補わない。

## 68. バックチャネル交換API

交換操作は`POST /auth/handoffs/exchange`とする。ブラウザから直接呼び出させず、CORSによるブラウザ利用を標準で許可しない。TLSを必須とする。

リクエスト本文はJSONで、最小限の入力は次とする。

```json
{"code":"opaque-handoff-code"}
```

`service_id`は本文から信用せず、認証済みWebサービス資格情報から決定する。`return_target`、`internal_user_id`、`state`を本文へ再送させない。

認証基盤は、サービス資格情報、サービス状態、コードの存在・未使用性・期限、コードの対象`service_id`、対応する内部ユーザー、元処理の正常完了、必要な状態取得を検証する。共通認証セッションが交換前に終了していれば交換を拒否する。交換成功とコードの使用済み化は論理的に一つの処理として成立させる。

## 69. Webサービスのバックチャネル認証

初期方式では、RegisteredWebServiceごとの不透明な`service_secret`をHTTP Basic認証で使用する。`username = service_id`、`password = service_secret`とし、TLS上でのみ使用する。

`service_secret`はブラウザ、フロントエンド、Cookie、URL、ログへ渡さない。これは認証結果の発行鍵ではない。保有するWebサービスに許可するのは自サービス向け未使用コードの交換だけである。コード発行、他サービス向け交換、任意の`internal_user_id`指定、認証結果の署名・偽造、共通認証セッション操作を許可しない。mTLS、JWT client assertion、動的クライアント登録は初期方式に追加しない。

## 70. 交換成功レスポンス

交換成功時のJSONは次の最小情報だけを返す。

```json
{"internal_user_id":"stable-internal-user-id","authenticated_at":"timestamp"}
```

メール、表示名、画像、外部provider、外部subject、外部トークン、共通認証セッションID・期限、JWT、Webサービス固有ロール・プロフィールは返さない。レスポンスを長期保存する認証トークンとして使用させず、ローカルセッション開始にだけ使用する。

## 71. Webサービス側ローカルセッション

Webサービスは交換成功後に自サービス固有のローカルセッションを開始する。`portal_backend`の基準方式はサーバー側ローカルセッションとし、ブラウザCookieには不透明なローカルセッションIDだけを保持する。Cookieへ`internal_user_id`や業務権限を直接格納せず、認証基盤とCookieを共有しない。

ローカルセッションは少なくとも`internal_user_id`、作成時刻、有効期限、認証成立時刻、有効または終了の状態に結び付く。保存先、Cookie名、ID形式は後続工程で決める。

## 72. Cookie契約

認証基盤の共通認証Cookieは、認証基盤ホストに限定するhost-only Cookieとする。`Domain`を親ドメインへ設定せず、`Path=/`、`Secure`、`HttpOnly`、`SameSite=Lax`を使用する。値は不透明な共通認証セッション参照情報であり、ユーザー属性やJWTを格納しない。

WebサービスCookieも対象Webサービスのhost-only Cookieとし、`Domain`を親ドメインへ設定せず、`Path=/`、`Secure`、`HttpOnly`、`SameSite=Lax`を使用する。値は不透明なローカルセッション参照情報とし、認証基盤Cookieと同じ名前や値を使用しない。

Cookie名と具体的な有効期限は後続工程で決める。

## 73. ログアウト契約

ローカルログアウトは各Webサービスが所有する。`portal_backend`の参照契約は`POST /logout`とする。Webサービス側ローカルセッションを終了し、WebサービスCookieを削除するが、認証基盤Cookieと共通認証セッションは変更しない。Webサービス自身のCSRF対策を必要とする。

共通ログアウトは認証基盤が所有する。初期方式は`GET /auth/logout`と`POST /auth/logout`の二段階とする。GETは`service_id`と`return_target`を受け、登録情報で検証した後、認証基盤ドメインの確認または実行ページを返す。このGETだけで共通認証セッションを終了しない。
GETで検証した`service_id`と`return_target`は、認証基盤が所有する短時間のログアウト一時状態へ保存する。POSTでは、ブラウザから再送された`service_id`や`return_target`を無条件に信用せず、この一時状態から取得する。一時状態が存在しない、期限切れ、使用済み、またはCSRF検証に失敗した場合は、共通認証セッションを終了しない。

POSTは認証基盤ドメイン上のページから認証基盤自身のCSRF対策を通して実行する。成功時に共通認証セッションを終了し、認証基盤Cookieを削除し、検証済み`return_target`へ戻す。既存のWebサービスローカルセッションは直接削除しない。対象が不在または終了済みでも安全な冪等操作として成功扱いにしてよい。

初期実装に一般的な失効照会APIを含めない。全リクエスト照会方式への回帰、通常利用への障害波及、状態とAPIの増加を避けるためである。既存の`/sessions/verify`を完成形として維持しない。

## 74. エラーと再試行

未登録サービス、停止中サービス、不正な戻り先は認証基盤上の安全なエラーとして終了し、未検証の戻り先へ返さない。検証済み戻り先では、外部認証拒否、期限切れ、認証未完了について必要最小限のエラーコードと元の`state`を返せる。外部プロバイダーの生エラー、内部エラー、Secret、トークンは返さない。

交換では`invalid_request`、`invalid_service`、`service_inactive`、`handoff_invalid`、`handoff_expired`、`handoff_already_used`、`handoff_service_mismatch`、`authentication_not_completed`、`temporarily_unavailable`を区別する。JSON・必須項目不備は400、サービス認証失敗は401、停止中サービスは403、無効・期限切れ・使用済み・対象不一致のコードは400、一時障害は503を基本とする。コードの存在や別サービス向けである事実を必要以上に公開しない。

交換成功後のコードは再交換できない。交換後にWebサービスが応答を受け取れなくても再交換可能にせず、新しいログインを開始する。交換結果再送キャッシュ、複雑な冪等性キー、複数回取得可能なコードは初期方式に追加しない。このため通信障害時はログインをやり直す可能性がある。

## 75. セキュリティ上の不変条件

- ブラウザとフロントエンドだけでログイン開始状態、認証成功、交換を成立させない。
- `state`と`handoff_code`を兼用しない。
- `state`、`handoff_code`、共通認証セッション、ローカルセッションを混同しない。
- 未検証の`return_target`へ遷移しない。
- 認証基盤CookieをWebサービスへ共有しない。
- `service_secret`と認証結果の発行鍵を混同しない。
- 交換失敗、不明状態、取得失敗を認証成功として扱わない。
- 認証開始、callback、交換、ログアウトの応答に認証情報を共有キャッシュへ保存させない。
- `handoff_code`、`service_secret`、Cookie、外部トークン、Google client secretをログへ平文記録しない。
- callback後はコードを早期に処理し、コードを含まないURLへ遷移する。

## 79. 保存設計の目的

永続的な本人対応関係、短期認証状態、Webサービス固有状態を別の正本として扱う。

## 80. 保存設計の基本原則

PostgreSQLは永続データ、Redisは認証基盤の短期状態、各Webサービスは自サービス状態を所有する。保存先障害をデータ不在や認証成功として扱わない。

## 81. 論理データと正本

| 論理データ | 所有者 | 正本 | 永続性 | 主な終了条件 |
|---|---|---|---|---|
| `InternalUser` | 認証基盤 | PostgreSQL | 永続 | ユーザーライフサイクル上の終了 |
| `ExternalIdentity` | 認証基盤 | PostgreSQL | 永続 | 明示的な関連解除 |
| `RegisteredWebService` | 認証基盤 | PostgreSQL | 永続 | 利用停止 |
| Webサービス資格情報 | 認証基盤 | PostgreSQL | 永続 | 無効化または置換 |
| 外部認証トランザクション | 認証基盤 | Redis | 短期 | 完了、失敗、期限切れ |
| 共通認証セッション | 認証基盤 | Redis | 短期 | ログアウト、失効、期限切れ |
| `AuthenticationHandoff` | 認証基盤 | Redis | 短期 | 交換成功による使用済み、期限切れ |
| 共通ログアウト一時状態 | 認証基盤 | Redis | 短期 | 使用、期限切れ |
| Webサービス側ログイン開始状態 | 各Webサービス | 各Webサービス | 短期 | 使用、期限切れ |
| Webサービス側ローカルセッション | 各Webサービス | 各Webサービス | 期限付き。具体値は各Webサービス方針 | ローカルログアウト、期限切れ |

## 82. PostgreSQLが所有する永続データ

`InternalUser`と`ExternalIdentity`はPostgreSQLの永続データである。外部本人の一意性は`(provider, subject)`で保証し、一つのExternalIdentityは一つのInternalUserだけを参照する。メールアドレスを一意性や自動統合の根拠にしない。

新しい外部本人ではInternalUser作成、ExternalIdentity作成、関連付けを一つのPostgreSQLトランザクションとして成立させる。既存の外部本人では対応する`internal_user_id`を取得する。一意性競合時は成功を推測せず再読込する。PostgreSQLの読込・書込失敗は認証成功にしない。

## 83. Webサービス登録と資格情報

RegisteredWebServiceはPostgreSQLの永続データであり、`service_id`、利用可能状態、許可済み`return_target`、Webサービス資格情報の検証情報に結び付く。初期実装は静的登録のみとし、動的登録、管理画面、自己登録を追加しない。登録情報を取得できない場合は未登録と推測せず保存先障害として失敗させる。

`service_secret`の平文をPostgreSQLへ保存せず、不可逆な検証情報だけを保存する。平文は各WebサービスのSecret管理領域に保持し、ブラウザ、Cookie、URL、通常ログへ渡さない。認証結果の署名鍵として使用せず、Webサービス間で共有しない。一つのサービスには初期状態で一つの現在有効な資格情報だけを持たせる。

## 84. Redisが所有する短期状態

Redisは外部認証トランザクション、共通認証セッション、AuthenticationHandoff、共通ログアウト一時状態の正本である。これらをPostgreSQLへ二重保存して復元・同期する機構を追加しない。Redis喪失時は認証をやり直すことを許容し、喪失・障害を認証成功として扱わない。

## 85. 共通認証セッション

共通認証セッションは不透明な参照情報、`internal_user_id`、作成時刻、認証成立時刻、絶対有効期限に結び付くRedis短期状態である。存在し、期限内で、必要な値を正常に読み取れた場合だけ有効と判断する。エントリ不在、期限切れ、Redis読込失敗を区別し、読込失敗をGoogle認証へのフォールバックにしない。ログアウトまたは失効ではサーバー側状態を終了し、Cookie削除だけを正本にしない。

## 86. 外部認証トランザクション

外部認証トランザクションは、対象`service_id`、検証済み`return_target`、Webサービスの`state`、外部プロバイダー、callback検証用の内部一時識別情報、作成時刻、期限、未処理または処理開始済みの状態に結び付くRedis短期状態である。

Webサービスの`state`と、認証基盤が外部callbackを対応付ける内部識別情報を混同しない。外部プロバイダーへWebサービスのstateをそのまま渡さない。callback受領時は処理開始済みへ原子的に遷移させる。同じcallbackを再処理して認証成功にしない。失敗時は新しいログインを開始する。

## 87. 認証引き渡し状態

AuthenticationHandoffは、`service_id`、`internal_user_id`、検証済み`return_target`、発行時刻、有効期限、未使用または使用済み、元の共通認証セッション、認証成立時刻に結び付くRedis短期状態である。平文`handoff_code`をログへ記録せず、保存側では不可逆に導出した検索用識別情報を使用する。期限切れ、未使用、使用済みを区別し、使用済み状態は少なくとも元の期限または短い診断保持期間まで保持できる。

## 88. 共通ログアウト一時状態

共通ログアウト一時状態は、対象`service_id`、検証済み`return_target`、作成時刻、有効期限、未使用または使用済み、認証基盤側CSRF検証情報に結び付くRedis短期状態である。GETで検証した値を保存し、POSTで同値が再送されたことだけを根拠にしない。POST成功では一時状態の使用済み化と共通認証セッション終了を論理的に一つの処理とする。

## 89. Webサービス側の状態

Webサービス側ログイン開始状態とローカルセッションは各Webサービスが所有し、認証基盤のPostgreSQLまたはRedisへ保存しない。開始状態は`state`、作成時刻、期限、使用状態、安全な内部遷移先に結び付く。state検証後は交換前に再利用不能にする。

ローカルセッションは不透明な参照情報、`internal_user_id`、作成時刻、認証成立時刻、有効期限、有効または終了状態に結び付く。Cookieは参照情報だけを持ち、internal_user_idや権限を直接格納しない。保存障害時はログインを失敗させ、使用済みhandoffを再利用しない。

## 90. PostgreSQLとRedisの役割分担

| 判断対象 | PostgreSQL | Redis | Webサービス側 |
|---|---|---|---|
| 永続性 | 本人対応、登録、資格情報の永続正本 | 短期状態のみ | 自サービス方針 |
| 一意性 | `(provider, subject)`と登録情報 | 一回限り使用状態 | ローカルstateとセッション |
| 期限 | 永続データでは主目的でない | 全短期状態で必須 | 自サービスで管理 |
| 原子的遷移 | 本人解決トランザクション | callback、handoff、ログアウト | state・ローカル状態 |
| 障害時 | 推測せず失敗 | 推測せず一時障害 | 自サービスの失敗 |
| 所有権 | 認証基盤 | 認証基盤 | 各Webサービス |

RedisをPostgreSQLのキャッシュとして扱わない。

## 91. 永続的な本人解決のトランザクション

新規外部本人の一意性確認、InternalUser作成、ExternalIdentity作成、関連付けは一つのPostgreSQLトランザクションとして成立させる。一部だけの作成を認証成功にしない。競合時は確定済み対応関係を再読込する。

## 92. SSOと初回認証における状態作成

SSOでは共通認証セッションの有効確認とhandoff発行を原子的な論理処理とする。初回認証ではinternal_user_id確定後、Redisで共通認証セッションとhandoffを両方作成する。片方だけを認証成功として返さない。

## 93. handoff交換の原子性

交換ではサービス認証、handoff取得、未使用性、期限、対象service_id、共通認証セッション有効性、必要値取得、使用済み化を一回の論理交換として扱う。同時交換では一つだけ成功し、残りは使用済みとして失敗する。

## 94. PostgreSQLとRedisをまたぐ部分失敗

分散トランザクション、二相コミット、分散ロック、汎用Sagaを導入しない。callbackでは、外部認証トランザクションを処理開始済みにし、外部結果を検証し、PostgreSQLで本人を解決し、Redisで共通セッションとhandoffを作成してから応答する。

PostgreSQL成功後のRedis失敗では永続本人データを残してよいが、認証成功を返さない。再試行では既存ExternalIdentityから同じinternal_user_idを取得する。Redis成功後の応答送信失敗では短期状態は期限まで残ってよい。handoff交換後のローカルセッション作成失敗ではhandoffを使用済みのままとし、新しいログインを開始する。

## 95. 期限切れと削除

外部認証トランザクション、共通認証セッション、AuthenticationHandoff、共通ログアウト一時状態は明示的な有効期限を持つ。物理削除だけに依存せず保存期限も検証する。TTLを基本とし、診断保持が必要な使用済みhandoffだけ論理期限と物理削除期限を分けられる。永続データを短期状態の期限切れで削除しない。

## 96. 障害とデータ消失

Redis再起動後の短期状態完全復元を保証しない。状態喪失時は外部認証のやり直し、共通認証セッション終了、handoff無効化、ログアウト操作のやり直しを許容する。保存されていたはずの状態を推測して復元しない。Redis永続化・可用性方式は後続工程で決める。

## 97. ログと正本の分離

通常ログと監査ログは認証状態の正本ではない。ログ欠落を成功根拠にしない。共通認証セッション参照情報、handoff_code、service_secret、ローカルセッション参照情報、外部トークン、外部プロバイダーclient secretを平文ログへ記録しない。専用永続監査DBは初期実装に追加しない。

## 98. 現在の実装との差分

| 現在の実装 | 今回固定した保存設計との差分 | 変更の方向 |
|---|---|---|
| PostgreSQLのusers | Google固有情報と本人概念が混在 | InternalUserとExternalIdentityへ分離する方向 |
| Google IDを直接ユーザー識別へ使う実装 | providerとsubjectの組でない | `(provider, subject)`を永続一意性にする方向 |
| Redis `session_id` | 内部値がブラウザへ露出 | 認証基盤内の短期正本へ閉じる方向 |
| `jwt` | ブラウザ認証結果として使用 | 不透明なコードとローカル状態へ分離する方向 |
| `/upsert_and_token` | 永続本人解決と短期状態を同時に返す | 永続処理と状態作成を分離する方向 |
| `/sessions/verify` | Redisを都度照会する | 一回限り交換を主方式にする方向 |
| `JWT_SECRET` | 発行可能な共有秘密 | service_secretと発行鍵を分離する方向 |
| `.tororomeshi.net`共有Cookie | 共通状態を共有する | host-only Cookieへ移す方向 |
| `ALLOWED_REDIRECT_ORIGINS` | 登録情報の永続正本でない | RegisteredWebServiceへ移す方向 |
| `portal_backend`の認証状態 | JWT直接検証 | 自サービスのローカル正本へ移す方向 |
| 現在のログアウト処理 | Cookie削除と状態終了が混在 | ローカルと共通状態を分離する方向 |

## 99. 今回固定する不変条件

- 永続データと短期認証状態を同じ正本にしない。
- Redis上の短期状態をPostgreSQLへ二重保存しない。
- Redisを今回の短期認証状態について単なるキャッシュとして扱わない。
- 保存先障害をデータ不在として扱わない。
- 取得できなかった値を正常値として扱わない。
- 部分的に作成された状態を認証成功として返さない。
- 外部本人の一意性を`(provider, subject)`で保証する。
- メールアドレスで自動統合しない。
- `service_secret`を平文保存せず、認証結果発行鍵として扱わない。
- 共通認証セッションとWebサービス側ローカルセッションを共有しない。
- Webサービスの状態を認証基盤の保存領域へ混在させない。
- handoff交換では同時実行の一つだけを成功させ、使用済みhandoffを再利用しない。
- 期限切れ状態を物理的に残っているだけで有効扱いしない。
- ログを認証状態の正本にしない。
- 短期処理失敗の補償として永続本人データを削除しない。
- 不明な状態を成功側へ倒さない。
